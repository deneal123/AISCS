# Инфраструктура платформы: перенос GPTHub и подключение research

Решение от **27 октября 2026 года** уточняет документы 02 и 04. Пользователь
потребовал перенос готовой инфраструктуры GPTHub, включая подготовку среды,
отдельные воркеры и beat. Прежний упрощённый контур не является целевой архитектурой.

## Источник и границы переноса

Из `R:/GPTHub` скопированы `docker/build.sh`, `run.sh`, `compose_preflight.sh`,
`sync_env.py`, подготовка локальной модели, исходные dev/prod Compose, Dockerfile
backend/frontend, entrypoints и отслеживаемые конфигурации `infra`.
Исходные GPTHub и Alter не изменяются. Данные контейнеров и TLS-ключи не переносятся.
Источник, хеши и прежние версии изменённых локальных файлов записаны в
`.work/generator-implementation/upstream-infrastructure.json` и `infra-before/`.

Профиль `simulation` использует `extends` исходных определений. Поэтому команды,
проверки готовности, bootstrap миграций, версии PostgreSQL и Redis наследуются,
а специфические изменения видны в двух небольших конфигурациях:

- `docker/docker-compose.simulation.yaml` — локальная разработка;
- `docker/docker-compose.simulation.prod.yaml` — подготовка AISCS production.

| Узел | Принятое решение |
|---|---|
| PostgreSQL | 17.4, исходный entrypoint backend и Alembic; собственные данные AISCS |
| Redis | 7.4, пароль, broker `/0`, результаты Celery `/1`, кэш и события |
| Celery | Отдельные beat, maintenance и simulation; simulation concurrency=1 |
| Agents worker | Сохранён, включается профилем `assistant`; для численного демо не обязателен |
| Хранилище dev | Отдельный локальный MinIO с исходной закреплённой версией; registry Quay вместо недоступного Docker Hub |
| Хранилище prod | Внешний S3 Selectel, бакет `aiscs`, без локальной подмены |
| Generator | Приватный HTTP-сервис, собственный токен, рабочий том |
| Ненужные возможности | Сохранены в исходном Compose; не включены в профиль симулятора |

Общие задачи обслуживания файлов и потоков сохраняются в beat. Чатовые, платёжные
и провайдерские расписания остаются в профиле GPTHub. Воркер симуляции не запускает
встроенный beat. Recovery направляется в `maintenance`, расчёты — в `simulation`.

`sync_env.py` дополняет только известные параметры и создаёт отсутствующие внутренние
секреты без ротации существующих. Ни логи, ни диагностика Compose не выводят значения.
В Git Bash можно указать `PYTHON_BIN`; предусмотрен рабочий Python 3 либо `uv`.

Исторические образы MinIO не загрузились: Docker Hub вернул `pull access denied`,
Quay — `401`. Первый стенд использовал отдельный локальный тег уже имеющегося образа;
это не считалось проверкой чистого развёртывания. Теперь профиль собирает
`aspa-minio-source:RELEASE.2025-09-07T16-13-09Z` по
[Dockerfile](../../../docker/minio/Dockerfile) из commit
`07c3a429bfed433e49018cb0f78a52145d4bedeb`. Проверены SHA-256 исходного архива,
upstream `go.sum`, версия бинарника и реальная запись/чтение десяти артефактов
в новом проекте с отдельными пустыми томами. Это наша сборка закреплённого исходного
кода, не побайтовая копия исторического контейнера.

Build context ограничен `docker/minio/`, `.dockerignore` пропускает только файлы
сборки. Приватные env не передаются в этот контекст. `MINIO_DEV_IMAGE` позволяет
задать тег; штатные build/run используют тот же сервис Compose. Порядок сборки и
проверки: [описание MinIO](../../../docker/minio/README.md). Production использует
внешний S3 и от локального образа не зависит.

## Production AISCS

По прямому разрешению пользователя приватный `docker/.env.prod` подготовлен из
production-среды GPTHub. Он игнорируется Git. Секреты поставщиков и почтовые настройки
сохранены как исходная конфигурация; идентичность приложения, пароли PostgreSQL/Redis,
JWT и внутренние ключи AISCS созданы отдельно. Ключи S3 намеренно пустые: их добавит
владелец после создания бакета. Production не запускался.

| Параметр | Значение |
|---|---|
| Публичный адрес | `https://aiscs.incellcorp.ru` |
| CORS backend | Только `https://aiscs.incellcorp.ru`, с существующими правилами credentials |
| Авторизация | `AUTH__AUTH_MODE=prod`, `AUTH__DEV_MODE=false`, защищённая cookie |
| Frontend | Профиль компилируется при сборке; API и WebSocket используют свой origin |
| S3 endpoint | `s3.ru-7.storage.selcloud.ru`, регион `ru-7`, TLS включён |
| Бакет | `aiscs` |
| Nginx внутри проекта | Исходный GPTHub proxy, WebSocket и Docker DNS; authority по образцу Alter |
| Внешний proxy | Существующий общий Nginx: домен AISCS → `https://127.0.0.1:8447` |
| TLS проекта | `infra/nginx/certs/aiscs/certificate.pem` и `private.pem`, вне Git |

Порт 8447 — предлагаемый отдельный локальный upstream, не часть публичного URL.
Проверить его свободность на целевом сервере до развёртывания. `PUBLIC_HTTPS_PORT=443`
описывает адрес браузера; при иной схеме одновременно изменить proxy, CORS и origin.
Внешний Nginx, DNS и сертификат этим проходом не изменяются.

Подготовлены безопасный перечень параметров `docker/prod.env.example` и S3 CORS
`infra/s3/aiscs-cors.json`. Последний нужен только для браузерного чтения объектов;
серверный доступ backend к S3 не зависит от браузерного CORS. Политика бакета не
делает файлы публичными. Применение выполняется после создания бакета владельцем.

До запуска проверить: S3 credentials и права на собственный бакет; TLS и DNS;
подключение edge proxy; HTTPS cookie; разрешённый/посторонний Origin; WS;
сохранение и скачивание файла; отдельные воркеры; миграции и резервное копирование.
Сейчас подтверждается конфигурация, а не работа production.

## Включение aspa-research — запланировано

Пользователь потребовал включить исследовательский сервис в общий порядок запуска,
а затем добавить отдельную страницу поиска. На этом шаге фиксируется план;
Compose research, его индекс и интерфейс не изменяются.

1. Сверить `research/docker/compose.knowledge.yaml`, текущий Docker project
   `aspa-research-knowledge`, имена реальных томов, сеть и указатель опубликованного
   поколения. Сохранить инвентарь и хеши. Не строить новый индекс ради подключения.
2. Добавить запуск существующего проекта research в общую оркестрацию build/run,
   сохранив его namespace и тома. Простой перенос сервисов в `aspa-dev` создаст
   новые пустые тома; такой перенос не допускается без отдельной миграции.
3. В состав включить сервис research, Neo4j, Qdrant и embedding gateway. Его runtime
   env и TLS доверие остаются в research; не смешивать с MemOS или векторами приложения.
4. Соединить backend с HTTP research через выделенную внутреннюю сеть. Не открывать
   научные хранилища в интернет. Зафиксировать сервисную авторизацию, таймауты,
   read-only операции и готовность. Недоступность research не блокирует численный
   опыт; в будущей странице показывается ошибка доступности или явный fallback.
5. В dev включать research штатным запуском после этой приёмки. Для prod отдельно
   перенести проверенное поколение, тексты/реестр и тома на сервер, сверить хеши и
   секреты. Локальная готовность не означает наличие корпуса в production.
6. Проверить повторный запуск без потери индекса, реальный hybrid retrieval,
   раскрытие графа, evidence locators и статус поколения. Не смешивать непроверенные
   связи с подтверждёнными по умолчанию.
7. Следующим шагом реализовать страницу `/research` в той же оболочке: вопрос,
   фильтры, hybrid/lexical режим, результаты с источником и локатором, контекст
   доказательства, связи графа и покрытие опубликованного поколения. Запросы идут
   через авторизованный backend; прямые пароли Neo4j/Qdrant браузеру не выдаются.

До выполнения пунктов запуск research остаётся самостоятельным. Действующие
контейнеры не останавливаются; канонические карточки и научные статусы сохраняются.
