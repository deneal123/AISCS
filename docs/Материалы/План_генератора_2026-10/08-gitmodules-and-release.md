## Алгоритм восстановления

1. Перед работой повторно сохранить HEAD, ветки, diff, untracked-инвентарь и хеши для каждого проекта. Сопоставить с исходным состоянием; работа параллельного агента не считается мусором.
2. Для каждого возвращаемого проекта найти последний подтверждённый gitlink и соответствующую запись `.gitmodules` в истории суперпроекта. Проверить происхождение источников и доступность commit в нужном remote.
3. При отсутствующих metadata подготовить отдельный checkout в игнорируемой `.work/`, сравнить файлы с текущим каталогом и сохранить отличия. Восстановить metadata без принудительного checkout/reset поверх пользовательских файлов. Неразрешённое происхождение блокирует регистрацию конкретного проекта, а не оправдывает фиктивный URL.
4. В `.gitmodules` согласовать `path`, проверенный URL и ветку там, где действительно используется ветка. В индекс добавить gitlink с режимом `160000` для каждого такого пути. Поле `branch` не заменяет закреплённый commit.
5. Для generator принять тот же способ доставки, что у собственных веток AISCS. До использования его gitlink создать и опубликовать проверенный commit ветки generator. Наличие ветки на origin проверяется, не предполагается.
6. Выполнить `git submodule sync --recursive` только после проверки итоговой карты. Не регистрировать `infra` и `scripts` как сабмодули без собственной истории: это файлы суперпроекта.
7. Проверить `.gitmodules ↔ индекс 160000 ↔ checkout HEAD ↔ remote commit`. Исключить вложенные `.git` как обычные файлы и случайное добавление содержимого целого сабмодуля в суперпроект.

Запрещены в этом алгоритме массовый `git add -A`, `reset --hard`, очистка пользовательских каталогов и смена upstream SIM ради удобства. Сохранённые файлы с нарушенной Git metadata сначала восстанавливаются, а не удаляются и клонируются поверх.

## Версии и порядок публикации

- Generator: первая предполагаемая версия пакета `0.1.0`, HTTP-контракт v1; версия научного пресета и хеш входов учитываются отдельно. Это будущие значения, не текущий выпуск.
- Backend/frontend: новая возможность требует согласованного minor bump от актуальной на момент выпуска версии. Обновить единственный источник версии, lock-файлы и runtime-представления там, где они существуют.
- Другие сайдкары: повышать версию при наличии проверенных изменений соответствующего проекта, а не для имитации синхронного изменения всех моделей. Данные research не повышают научную схему только из-за выпуска платформы.
- Для суперпроекта зафиксировать совместимый набор SHA и версий в описании выпуска; теги применять по принятому в проекте соглашению после проверки.

Порядок: проверки → просмотр diff и секретов → явное добавление проверенных путей → отдельные коммиты изменённых сабмодулей → push их веток в origin → сравнение удалённых SHA → обновление gitlink суперпроекта → коммит и push `dev` → проверка удалённого суперпроекта и его ссылок.

Перед push получать актуальную историю remote. При параллельных изменениях сначала согласовать и проверить итоговое дерево; force-push не является штатным способом выпуска. Изменения research, выполненные другим агентом, учитываются по фактическому diff и его проверкам, не присваиваются этому проходу.

## Приёмка выпуска

- Все возвращённые проекты имеют подтверждённые URL/HEAD и рабочую Git metadata.
- В суперпроекте нет файлов окружения, секретов, весов внешних моделей, исходных полных текстов, контейнерных данных, кэшей и worker-ответов. Компактный линейный классификатор `generator/validation/demo-v1/` — намеренный воспроизводимый демо-артефакт с протоколом и ошибками; сырые записи в Git не включаются.
- Концепты `visuals/` — намеренные документы проекта; исходные временные генерации и невыбранные варианты не добавляются.
- Проверены нужные тесты каждого изменённого проекта, общий контракт, Compose и сквозной опыт; документационная проверка не подменяет их.
- Чистый независимый clone с submodules получает все обязательные исходники и закреплённые commits. Кэши и текущая `.git/modules` не являются скрытой зависимостью.
- Каждый gitlink удалённого `dev` указывает на уже опубликованный и доступный commit; удалённые SHA совпадают с принятыми локальными.

Публикация остаётся незавершённой, если хотя бы один обязательный commit доступен только локально.
