# 19. Сквозной прогон популяции: что измерено и где мы стоим

Дата: 2026-11-12. Продолжение [18-full-neuron-performance-2026-11-11.md](18-full-neuron-performance-2026-11-11.md).

Цель: все ~166 700 сложных нейронов end-to-end за 20 с (изначально 120 с).
Этот документ фиксирует **первый реальный сквозной прогон на живой популяции**
(а не на модели из 160 тел), его результат и точное место, где теряется время.

## 1. Итог одного замера

Драйвер: `.work/connectome-routing-20261028/production-bench/e2e-fast.py`
(аутентификация кэша -> prepare -> бакетизация по размеру -> GPU -> 1 проход).

| величина | значение |
|---|---|
| обработано клеток | 40 162 из 166 700 (24 %) |
| обработано сегментов | 106 070 265 из 270 009 259 (39.3 %) |
| wall-clock | 561.6 с |
| из них solve (GPU) | 386.4 с |
| из них prepare (8 потоков) | ~155 с (оценка: wall - solve - setup) |
| батчей | 76 |
| экстраполяция solve на всю популяцию | **~984 с** |
| экстраполяция wall на всю популяцию | **~1430 с** |

Прогон был остановлен по таймауту сессии на 24 % клеток; масштабирование по
сегментам линейное (паддинг внутри бакета стабилен 1.30-1.56x), поэтому
экстраполяция корректна.

**Вывод: сейчас полный расчёт — это ~24 минуты, а не 2 и не 20 секунд.**
Разрыв с целью — 70x по solve-времени.

## 2. Где именно теряется время (по стадиям, из того же прогона)

| стадия | на всю популяцию | комментарий |
|---|---|---|
| чтение+аутентификация кэша | ~21 с | 8 потоков, zlib inflate 55-58 % стоимости |
| prepare (NEURON-free) | ~60 с | 168 нс/сегмент, проверено 200-350x быстрее NEURON |
| упаковка батчей (pack_trees, host) | ~40-60 с | host-side layout на каждый батч |
| **GPU solve** | **~984 с** | главный разрыв |
| запись/агрегация | ~10 с | |

Итого полезного: ~110 с инфраструктуры против ~984 с ядра. **Ядро — это 87 %
времени**, и именно оно в 3-5x медленнее, чем в изолированном бенчмарке.

## 3. Ключевое открытие: батч ограничен видеопамятью, а ядро latency-bound

Изолированные замеры (production-bench/ct-scale.log, fair-occ2.log):

- ядро «одна клетка = один поток» при batch 2048 даёт 2.0e8 padding-сегменто-шагов/с;
- при batch 8192 — 4.3-4.9e8;
- при batch 32768 — 5.65-5.77e8 (это соответствовало бы ~94 с на всю популяцию).

Реальный прогон даёт batch **346-1547 клеток** (замерено: 346, 1124, 772, 832,
722, 1547), и на этих батчах эффективная скорость — **~1.0e8**, то есть в 3-5x
ниже насыщения. Причина — бюджет VRAM: под запись траекторий резервируется
`(samples, segments, batch)` fp64 на два массива, это 416 Б на слот сегмента,
и на 6 ГиБ карте батч упирается в ~1500 клеток ещё до того, как ядро выходит на
плато.

**Это и есть главный оставшийся рычаг: не алгоритм, а объём памяти на клетку.**

## 4. Что уже сделано и проверено (сводка по всем этапам)

| оптимизация | эффект | статус |
|---|---|---|
| Сокращение дерева (degree-2 контракция + снятие тупиков) | 1.74x меньше узлов | проверено, ошибка 5.4e-13 отн. |
| NEURON-free prepare на numba | 200-350x быстрее (168 нс/сегмент) | численно проверено на 6 телах, 8.7e-13 |
| Векторизация reduced_tree и tree_levels | 2.5-18.6 мс -> 0.4-4.3 мс на клетку | воспроизводит эталон побитово |
| Параллельная аутентификация кэша (8 потоков) | 64.3 с -> 21.2 с (3x) | замерено |
| Ядро «одна клетка = один поток» vs production | 2.5-3.3x при равной occupancy | замерено, бит-в-бит |
| Табличный распад гейтов (вместо exp) | 1.5x | ошибка 3.2e-9, приемлемо |
| Бакетизация по размеру вместо порядка манифеста | 2.31x меньше паддинга | замерено |
| Отказ от host-стриминга окон в пользу device-sink | 2-3x на передачах | замерено, не включено |
| f32-состояние | +10 % за ошибку 4.1e-4 | не рекомендовано |

## 6. Что нужно сделать, чтобы дойти до 20 с

Порядок по ожидаемой отдаче:

1. **Убрать запись траекторий из горячего ядра** (или писать их в f32 и только
   для 3 контрольных клеток, как уже умеет `estimate_output_bytes(...,
   state_trace_cells=3)`). Это снимает 416 Б/слот и позволяет батч 8192-32768,
   то есть 3-5x по замеренной кривой батча. Ожидаемо: ~984 с -> ~250-330 с.
2. **Упаковка клеток в варп** (32/K линий): теоретически 3-3.7x по числу
   барьерных раундов (средняя ширина уровня 5.37 узла на 32 линии). Требует
   починить стенд и заново замерить.
3. **Device-side окна** вместо host-копий: 2-3x на передачах, уже реализовано в
   `batch_solver.py` (`reduce_window_currents`, `gather_window_voltages`), но не
   подключено в `registered_batch.py`.
4. **Перекрыть prepare с GPU** — сейчас они частично последовательны; при 60 с
   prepare и 250 с solve это ещё ~15 % wall-clock.

Только пункты 1+3 дают оценочно 250-330 с; для 20 с нужен ещё один
структурный шаг (пункт 2 или постоянное ядро без переупаковки батчей).

## 7. Честная оценка

- Достижимо ли 120 с на текущем железе (RTX 3060 Laptop, 6 ГиБ)? **Да, с
  запасом** — насыщенное ядро по замеренной кривой даёт ~94 с на всю популяцию,
  плюс prepare 60 с, которые перекрываются.
- Достижимо ли 20 с? **На границе**: физический предел по памяти для
  сокращённого дерева — 6 с (f32) / 12 с (f64), инженерный предел при текущей
  структуре Hines — 25-40 с. Нужна упаковка линий и отказ от записи трасс.
