# Порядок испытаний и ведения материалов

## Одна запись — несколько представлений

Основная запись о кандидате — `data/registry.json`. Профиль исполнения находится в `data/profiles.json`. Итоговый разбор в `launch_review` содержит дату испытания, область проверки, квитанции, измерения, существенные исправления, преимущества, ограничения, три варианта продолжения и предварительное решение.

[TODO](../TODO.md), [REPORT](../REPORT.md), `data/assessment.json` и индексы [визуальных результатов](../artifacts/README.md) формируются `scripts/report.py`. Их не дополняют вручную хронологией. Проверка `--check` ничего не записывает и обнаруживает расхождения с реестром. Дата редакторской уборки не заменяет дату испытания.

## Последовательность для каждого SIM

1. Проверить URL, закреплённый commit, чистоту сабмодуля, зависимости и лицензии кода и данных. Не обновлять upstream одновременно с испытанием закреплённой версии.
2. Проверить идентичность входов: версия, первичный URL, размер, SHA-256 и доступность. Для недоступного зарегистрированного маршрута выполнить не более двух попыток. Не подменять недоступные данные другой версией.
3. Создать рабочую копию через `scripts/simctl.py evaluate --id SIM-xxx`. Устанавливать зависимости в изолированной среде. Сохранять разрешённые версии и `pip check`, если применимо.
4. Выполнить штатные тесты. При их отсутствии явно обозначить собственные программные проверки; синтаксический разбор не называть функциональным испытанием.
5. Выполнить минимальный запуск, затем доступные функциональные сценарии: входы, стимуляция, подавление, состояние, движение, reset и экспорт. Для аналитических проектов проверять их собственные операции подготовки и анализа данных.
6. Проверить единицы, размерности, конечность значений; короткие сценарии повторить с seeds 1, 2, 3 и повтором 1, где это применимо. Раздельно фиксировать повторяемость тела, сокращённой сети, полного графа и подготовки данных.
7. Сохранить визуальные результаты, открыть их и проверить соответствие сценарию. Для интерфейса — реальный скриншот; для численного результата — график из фактического экспорта. Отсутствие интерфейса не требует вымышленного изображения.
8. Записать итог и ограничения в `launch_review`. Успешный запуск не означает биологическую достоверность. При блокировке указать наблюдаемую причину и воспроизводимую команду; затем перейти к следующему SIM.
9. Опубликовать зарегистрированные визуальные файлы. Выполнить `scripts/cleanup.py --id SIM-xxx --apply --docker`, затем пересоздать представления и выполнить `scripts/check.py`. Уборка обязательна до перехода к следующему SIM; она не закрывает незавершённые научные или функциональные проверки.

## Визуальные материалы

Браузерный драйвер готовится командой `research/.venv/Scripts/python.exe -B simulations/scripts/prepare_browser.py` из корня суперпроекта. Закреплённые npm-манифесты находятся в `simulations/environments/browser-tools/`, зависимости устанавливаются в игнорируемой `.work/simulator-evaluation/browser-tools/`. Используется установленный браузер; отдельный Chromium не скачивается. После уборки драйвер при необходимости готовится заново.

Каждый SIM имеет отдельный каталог `artifacts/SIM-xxx/`: README с пояснениями, `manifest.json` с происхождением и контрольными суммами, проверенные PNG/PDF/MP4/SVG/WebM. При отсутствии результатов README сохраняет явную незавершённость визуальной проверки.

В `visual_artifacts` основной записи указать `file`, `source`, `sha256`, `caption` и `scope`. `source` указывает на собственный прогон этого SIM внутри `.work`. `scope` различает авторский вывод, диагностический график из экспорта, демонстрацию тела, нейродинамику и интерфейс. Для производного рисунка дополнительно сохранить команду, входные хеши и параметры в квитанции прогона.

`scripts/publish_artifacts.py` проверяет источник и копирует перечисленные файлы. Произвольные изображения из репозитория не выдаются за результаты испытаний. Большие исходные данные, зависимости, веса, ответы работников и логи не переносятся в галерею. Повторный прогон заменяет одноимённый принятый результат после проверки; архивные копии автоматически не создаются. Изображения не удаляются автоматически.

## Исполнение и ошибки

Перед запуском следующего SIM проверить план `scripts/cleanup.py`; `--apply` удаляет только известные временные каталоги внутри рабочей области. Уборка сохраняет квитанции, численные экспорты, первичные входы в единственном экземпляре и опубликованные визуальные материалы. Повторные копии входов удаляются после совпадения SHA-256. Квитанция уборки содержит удалённые пути, объём, сохраняемые экземпляры и проверку неизменности доказательств. Общие Docker volumes и build cache других проектов не очищаются.

После удаления окружения прежний прогон нельзя продолжать с пропуском установки. Для повторного испытания создать новый прогон и восстановить зависимости по сохранённым версиям. Для собственного образа сохранить Dockerfile и команду сборки в профиле. Временные данные не считать частью архива результатов.

Один вычислительный сценарий одновременно, до четырёх CPU-потоков. По решению пользователя лимит RAM и требование резерва отключены; фактическое потребление измеряется. Установка: до 30 минут, минимальная проверка: до 10, функциональная: до 30. GPU учитывается отдельно.

Истечение времени опроса Docker означает отсутствие наблюдения, а не завершение расчёта. Не перезапускать работающую задачу по одному сбою мониторинга. При прекращении по сроку завершать только собственный контейнер и фиксировать причину и подтверждение остановки. Чужие контейнеры и службы не останавливать.

Исправления вносятся в профиль или рабочую копию; сабмодули остаются чистыми. Исторические квитанции и команды не переписываются после переноса скриптов. Исторический инвентарь может отличаться от последующих опубликованных редакций; его нельзя заменять ради зелёной проверки.

## Границы исследования

Сохраняются 35/43, `G0_REVISE`, `saturation=false` и 15 неранжированных вариантов. Ноцицепция, субъективная боль, ECAP и клинические исходы различаются. Игровое повреждение не является биологической ноцицепцией. Генератор синтетического ECAP — будущая задача по [требованиям](generator-requirements.md); выбор собственной реализации, адаптации или композиции выполняется после сопоставимых испытаний.
