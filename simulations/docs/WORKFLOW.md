# Порядок испытаний и ведения материалов

## Одна запись — несколько представлений

Основная запись о кандидате — `data/registry.json`. Профиль исполнения находится в `data/profiles.json`. Итоговый разбор в `launch_review` содержит дату испытания, область проверки, квитанции, измерения, существенные исправления, преимущества, ограничения, три варианта продолжения и предварительное решение.

[TODO](../TODO.md), [REPORT](../REPORT.md), `data/assessment.json` и индексы [визуальных результатов](../artifacts/README.md) формируются `scripts/report.py`. Их не дополняют вручную хронологией. Проверка `--check` ничего не записывает и обнаруживает расхождения с реестром. Дата редакторской уборки не заменяет дату испытания.

## Последовательность для каждого SIM

1. Проверить URL, закреплённый commit, чистоту сабмодуля, зависимости и лицензии кода и данных. Не обновлять upstream одновременно с испытанием закреплённой версии.
2. Проверить идентичность входов: версия, первичный URL, размер, SHA-256 и доступность. Для недоступного зарегистрированного маршрута выполнить не более двух попыток. Не подменять недоступные данные другой версией.
3. Создать рабочую копию через `scripts/simctl.py evaluate --id SIM-xxx`. Устанавливать зависимости в изолированной среде. Сохранять разрешённые версии и `pip check`, если применимо.
4. Выполнить штатные тесты. При их отсутствии явно обозначить собственные программные проверки; синтаксический разбор не называть функциональным испытанием.
5. Выполнить минимальный запуск, затем доступные функциональные сценарии: входы, стимуляция, подавление, состояние, движение, reset и экспорт. Для аналитических проектов проверять их собственные операции подготовки и анализа данных.
6. Проверить единицы, размерности, конечность значений; короткие сценарии повторить с seeds 1, 2, 3 и повтором 1, где это применимо. Раздельно фиксировать повторяемость тела, сокращённой сети, полного графа и подготовки данных.
7. Сохранить визуальные результаты, открыть их и проверить соответствие сценарию. Для интерфейса — реальный скриншот; для численного результата — график из фактического экспорта. Отсутствие интерфейса не требует вымышленного изображения.
8. Записать итог и ограничения в `launch_review`. Успешный запуск не означает биологическую достоверность. При блокировке указать наблюдаемую причину и воспроизводимую команду; затем перейти к следующему SIM.
9. Опубликовать зарегистрированные визуальные файлы. Выполнить `scripts/cleanup.py --id SIM-xxx --apply --docker`, затем пересоздать представления и выполнить `scripts/check.py`. Уборка обязательна до перехода к следующему SIM; она не закрывает незавершённые научные или функциональные проверки.

## Визуальные материалы

Браузерный драйвер готовится командой `research/.venv/Scripts/python.exe -B simulations/scripts/prepare_browser.py` из корня суперпроекта. Закреплённые npm-манифесты находятся в `simulations/environments/browser-tools/`, зависимости устанавливаются в игнорируемой `.work/simulator-evaluation/browser-tools/`. Используется установленный браузер; отдельный Chromium не скачивается. После уборки драйвер при необходимости готовится заново.

Каждый SIM имеет отдельный каталог `artifacts/SIM-xxx/`: README с пояснениями, `manifest.json` с происхождением и контрольными суммами, проверенные PNG/PDF/MP4/SVG/WebM. При отсутствии результатов README сохраняет явную незавершённость визуальной проверки.

В `visual_artifacts` основной записи указать `file`, `source`, `sha256`, `caption` и `scope`. `source` указывает на собственный прогон этого SIM внутри `.work`. `scope` различает авторский вывод, диагностический график из экспорта, демонстрацию тела, нейродинамику и интерфейс. Для производного рисунка дополнительно сохранить команду, входные хеши и параметры в квитанции прогона.

`scripts/publish_artifacts.py` проверяет источник и копирует перечисленные файлы. Произвольные изображения из репозитория не выдаются за результаты испытаний. Большие исходные данные, зависимости, веса, ответы работников и логи не переносятся в галерею. Повторный прогон заменяет одноимённый принятый результат после проверки; архивные копии автоматически не создаются. Изображения не удаляются автоматически.

Если штатные тесты создают изображения или видео во временном каталоге, сохранить их **до уборки**. Для FlyGym Gymnasium после завершения контейнера:

```powershell
research/.venv/Scripts/python.exe -B -X utf8 simulations/scripts/retain_visuals.py --run research/.work/simulator-evaluation/SIM-021/<run> --from tmp/flygym_test
```

Команда проверяет размещение исходных файлов, сохраняет побайтные копии в `exports/native-tests/` и квитанцию `native-visuals.json`. Работающий контейнер с этим каталогом блокирует перенос. Затем просмотреть изображения, проверить декодирование видео и зарегистрировать принятые файлы в `visual_artifacts`; для штатного тестового вывода явно указать его происхождение. Само сохранение файла не подтверждает биологическую функцию. После публикации временные оригиналы можно удалить штатной уборкой.

## Повторный обход незакрытых проверок

После первоначального разбора всех 32 кандидатов повторно пройти каждый незакрытый пункт `TODO.md`. Сначала сопоставить его критерий с текущими первичными данными и последней квитанцией; исторический отказ из-за прежнего резерва RAM не считать действующей блокировкой. Проверить, изменились ли доступность данных, зависимости, ошибки адаптера или условия запуска.

Если причину можно устранить в разрешённой рабочей копии или профиле, исправить её и выполнить соответствующую проверку заново. Прежнюю неудачную квитанцию сохранить, новую записать отдельно. Для недоступных первичных маршрутов сохраняется общий журнал попыток: повторный обход не обнуляет установленный предел двух попыток. Если условие не изменилось, подтвердить конкретную причину текущим чтением, проверкой версии, состава файлов или доступности среды; не заменять её предположением.

Закрывать только проверенный критерий. Успешная установка не закрывает функциональный сценарий, небольшая fixture-сеть не заменяет зарегистрированный граф, а проверка готовых результатов не воспроизводит отсутствующий генератор. Итог повторного обхода записать в квитанциях и основном реестре; `TODO.md` и `REPORT.md` затем сформировать штатным генератором. Сохраняющиеся блокировки описать явно, не менять научные статусы и не выбирать архитектуру генератора автоматически.

## Исполнение и ошибки

Перед запуском следующего SIM проверить план `scripts/cleanup.py`; `--apply` удаляет только известные временные каталоги внутри рабочей области. Уборка сохраняет квитанции, численные экспорты, первичные входы в единственном экземпляре и опубликованные визуальные материалы. Повторные копии входов удаляются после совпадения SHA-256. Квитанция уборки содержит удалённые пути, объём, сохраняемые экземпляры и проверку неизменности доказательств. Общие Docker volumes и build cache других проектов не очищаются.

Уборка отдельного `--id` также включает общий pip-кэш этого контура в `research/.work/simulator-evaluation/pip-cache`. Кэш сохраняется, если смонтирован в работающий контейнер. Системный pip-кэш пользователя и кэши других проектов не затрагиваются.

Профиль Python может задать `environment_storage: docker-volume`. Тогда venv `/work/env` хранится в отдельном Linux-томе с метками владельца и SIM; исходники, входы, lock-файл и экспорты остаются в `.work`. Том общий только для контейнеров одного прогона и удаляется при выходе, включая отказ фазы. `--resume` такого окружения не поддерживается. Неудачное удаление фиксируется как `cleanup_pending`; `cleanup.py --docker` также проверяет оставшиеся собственные тома. Том с ссылкой из любого контейнера не удаляется, принудительное удаление не используется.

После удаления окружения прежний прогон нельзя продолжать с пропуском установки. Для повторного испытания создать новый прогон и восстановить зависимости по сохранённым версиям. Для собственного образа сохранить Dockerfile и команду сборки в профиле. Временные данные не считать частью архива результатов.

Для отдельной визуализации можно использовать `visual-followup/`. Перед очисткой в `runtime.json` зафиксировать `owner=simctl`, ID кандидата, завершённый статус, имена временных каталогов `env`/`mpl` и пути с SHA-256 сохранённых результатов вне этого каталога. Штатная очистка проверяет их принадлежность и целостность; неизвестные каталоги, активные mounts и доказательные файлы сохраняет. Сначала просмотреть план без `--apply`. Общую очистку Docker/BuildKit не выполнять; допускаются только точно установленные собственные ресурсы.

SIM-002 получает исходные файлы из зарегистрированного авторского RAR5, а не из HTML страницы подтверждения Google Drive. Архив и четыре выбранных файла закреплены SHA-256; журнал двух попыток сохраняется. `FiringRateNetwork` испытан на полном v630 с исходным масштабом конструктора, который отличается от CLI. Свежий прогон не воспроизводит подгонку параметров статьи. После очистки рабочие копии входов восстанавливаются из сохранённого проверенного оригинала.

SIM-004 использует собственный образ из `environments/escape-octave.Dockerfile`; его надо собрать явной командой `image_build` из профиля до запуска. Наличие поля в JSON само по себе не пересобирает образ. Альтернативная среда Octave и проверки отдельных функций не доказывают эквивалентность MATLAB. Отсутствующие SCAPE-измерения, Excel и файл GUI остаются блокировками полного анализа.

Профиль может указывать `environment_dir` и `dependency_lock`: для Julia это depot и TOML-манифест, для Python по умолчанию — `env/` и `dependencies.lock.txt`. Возобновление проверяет их наличие, закреплённые исходники и команды. Изменение команды установки или содержимого проверочных скриптов отменяет использование прежнего положительного результата. Функциональный сценарий при возобновлении выполняется заново. Метаданные предыдущих фаз сохраняются вместе с логами, временем и измеренной памятью.

После провала штатного теста продолжение возможно только для явно объявленного диагностического профиля `diagnose_after_native_failure`, с указанной причиной. Неуспешный тест остаётся в квитанции и препятствует статусу полного воспроизведения. Прерывание по ресурсам или времени этим режимом не обходится. Результаты дополнительных проверок описывают фактически выполненные операции, а не отменяют исходный провал.

Зафиксированные входы SIM-010 повторно читаются из `frozen_inputs` после проверки SHA-256 манифеста и каждого файла. Отсутствие или изменение сохранённого входа — блокировка, а не повод незаметно загрузить другую версию по прежнему URL. При повторном копировании сохраняется исходная дата получения; сетевые обращения не выполняются. Уборка удаляет копии только после совпадения хешей с сохранённым оригиналом. Для подписей графиков можно указать установленный шрифт через `ASPA_SIM_FONT_FILE`; временная копия шрифта не публикуется и удаляется с окружением.

Read-only-файлы зависимостей, создаваемые Julia, удаляются внутри проверенного временного дерева после снятия атрибута только у обычных файлов. Символьные ссылки и Windows reparse points не обходятся; первичные входы и доказательства не входят в это дерево.

Для SIM-011 Python-каскад и R-анализ имеют отдельные профили и результаты. После завершения `simctl.py evaluate --id SIM-011` R-проверка запускается командой `simulations/scripts/probes/banc_r_evaluate.py <путь-прогона>` тем же Python из корня проекта. Она использует `r_profile`, сохраняет `r-result.json` и не запускается одновременно с вычислительным процессом SIM-011. Библиотека R находится в `r-library/` и удаляется штатной уборкой. Общий `id` многоверсионного снимка не заменяет явный `root_888`; изменения индексирования каскада фиксируются отдельно от исходного модуля. Успех адаптированного сценария не отменяет провал проверок исходного алгоритма.

Один вычислительный сценарий одновременно, до четырёх CPU-потоков. По решению пользователя лимит RAM и требование резерва отключены; фактическое потребление измеряется. Установка: до 30 минут, минимальная проверка: до 10, функциональная: до 30. GPU учитывается отдельно.

Истечение времени опроса Docker означает отсутствие наблюдения, а не завершение расчёта. Не перезапускать работающую задачу по одному сбою мониторинга. При прекращении по сроку завершать только собственный контейнер и фиксировать причину и подтверждение остановки. Чужие контейнеры и службы не останавливать.

Исправления вносятся в профиль или рабочую копию; сабмодули остаются чистыми. Исторические квитанции и команды не переписываются после переноса скриптов. Исторический инвентарь может отличаться от последующих опубликованных редакций; его нельзя заменять ради зелёной проверки.

В частичных Git-клонах инвентарь имён снимается через `git ls-tree -r --name-only` с `GIT_NO_LAZY_FETCH=1`. Полный обход с `--long` способен неявно загружать отсутствующие blobs. Нужные небольшие экспорты получают по отдельным закреплённым объектам с проверкой Git-хеша и SHA-256. Для SIM-012 это два авторских SWC; их чтение не считается новой реконструкцией или подтверждением materialization v840. Численные координаты повторяются, тогда как случайные ID штатного экспорта аннотаций учитываются отдельно. Каталоги `build`, `dist` и `*.egg-info` удаляются только при отсутствии закреплённых исходников внутри них.

## Отдельные контуры SIM-013 и SIM-014

SIM-013 использует `execution_controller=conn_esn_linux`. Контроллер сохраняет один Linux-контейнер на время установки, штатного сценария и собственных проверок; зависимости находятся в `/opt/aspa-julia`. Это устраняет накладные расходы множества мелких файлов на Windows bind. Память каждой последующей фазы отражает накопленный пик этого контейнера. После завершения требуется проверка удаления контейнера; ошибка связи с Docker не доказывает его отсутствие. Повторный запуск создаёт новый прогон. Для адресной исправляющей попытки контроллер принимает `--cache-from <предыдущий-прогон-SIM-013>`: прежний временный depot монтируется только для чтения, его перенос и хеш фиксируются. Это не возобновление успешной фазы и не отменяет её первоначальный результат.

Явный флаг контроллера `--keep-runtime-on-failure` оставляет контейнер после частично выполненного прогона для адресной диагностики с уже собранными зависимостями. Прерывание по времени этот режим не отменяет: контейнер завершается. Удержанный контейнер отмечается в квитанции и должен быть удалён по точному имени с проверкой владельца до перехода к следующему SIM; затем выполняется обычная уборка каталогов. Обычная команда CLI не включает этот флаг.

Шесть входных матриц SIM-013 закреплены через `frozen_inputs`: проверяются SHA-256 манифеста, SHA-256 каждого CSV и Git-хеш исходного объекта. Повторное использование сохраняет исходную дату получения и отдельно фиксирует дату копирования. Перед удалением копии уборка сверяет её размер и хеш с сохраняемым первичным экземпляром. Длинные Windows-пути и read-only файлы обрабатываются только внутри уже проверенного временного каталога.

После функционального сценария профиль SIM-013 выполняет дополнительный `native_repl`: неизменённый авторский пример запускается через `Base.include(REPL.softscope, Main, script)`. Его результат и рисунок учитываются отдельно от отказа прямого CLI. Экспорт траекторий проверяет ненулевой отклик, первый шаг, сброс и нулевой вход; независимый повтор сравнивает JSON и CSV. Время задачи памяти сохраняется отдельно от численных результатов.

Для SIM-014 подготовлен отдельный сценарий с явно альтернативными данными FAFB v783. Авторский README не фиксирует точную материализацию исходного графа. Поэтому даже успешный запуск на v783 не будет воспроизведением авторской карты ориентаций. Три ранее полученных первичных gzip-экспорта проверяются по сохранённому манифесту и SHA-256; распакованные CSV создаются в `cache/flywire` и удаляются штатной уборкой. Скелеты, не используемые данным LIF-входом, не скачиваются. Проверка на четырёх нейронах обозначена как программный пример; короткий сценарий на альтернативном графе учитывается отдельно от полного авторского анализа.

SIM-015 использует прежний API FlyGym 1.x; выбран FlyGym 1.2.0 с NumPy 1.26.4, MuJoCo 3.2.7 и отдельным CPU-профилем PyTorch. [Официальное описание смены API](https://neuromechfly.org/migration/) не позволяет подменить его текущим FlyGym 2.x без адаптации. Разрешённые зависимости после первой установки фиксируются в lock-файле и используются для повторного прогона. Для OpenCV в минимальном Linux-образе дополнительно требуется системная библиотека GLib; ошибка её отсутствия остаётся в первой квитанции.

Таблицы SIM-015 повторно используются из проверенного первичного экземпляра SIM-006: Parquet совпадает побайтно, CSV после явно записанного преобразования CRLF → LF совпадает с Git-объектом закреплённого claude-fly. Авторские LFS-веса имеют отдельные размер и SHA-256. Если после двух попыток и проверки официального LFS API объект отсутствует, этот статус закрепляется; повторный прогон не начинает новые загрузки. ### SIM-026: доступ к геометрии и аннотациям

`simctl.py evaluate --id SIM-026 --no-memory-limit --no-host-reserve` устанавливает отдельное окружение для четырёх закреплённых notebook. Авторского lock и штатного набора тестов нет. Совместимое семейство Python 3.12/NumPy 2/MeshParty 2 зафиксировано профилем и фактическим lock; оно не выдаётся за исходную среду автора. Штатная функция `remap_seg` проверяется на явно искусственных uint64-метках и на реальном срезе. Цветовые номера не используются как исходные ID.

Функциональные области проверяются отдельными процессами: сегментация v630 и EM FAFB v14 в координатах примера; все 78 поверхностей областей v5 и проверка двух точек; две нейронные сетки v783, общий нейропиль и mesh/LOD2 v630; отдельная попытка CAVE. Пять URL, размеры и SHA-256 метаданных закреплены в реестре; при пустом рабочем каталоге загрузчик получает их заново. Журнал ограничивает неудачную загрузку двумя попытками и не сбрасывает счётчик при повторе; изменённый существующий файл сохраняется с ошибкой. Для объёмов задано `fill_missing=False`: недоступные блоки не заменяются нулями. Живые метаданные должны совпасть с проверенным срезом; версии и геометрия разных выпусков не объединяются по одному совпавшему root ID.

В EGL/Mesa-окружении проверенного VTK 9.7.1 штатный FXAA MeshParty давал чёрные PNG при успешном завершении команды. Поэтому адаптер явно отключает FXAA, сохраняя камеру, акторы, геометрию и масштаб 4×. Проверка наличия красной и синей геометрии обязательна: сам файл и код возврата 0 не означают успешной визуализации. Исходные неудачные изображения, малые диагностические тесты и исправленные полные кадры учитываются раздельно. Это настройка изображения, а не изменение анатомических данных.

```powershell
research/.venv/Scripts/python.exe -B -X utf8 simulations/scripts/probes/flyconnectome_check.py --run research/.work/simulator-evaluation/SIM-026/<run>
```

Контроллер создаёт собственный временный Linux-том, сверяет NPY/NPZ, размерности, исходные ID, координатные сетки и положение точек. Рендер проверяется на программном примере и повторяется на полных экспортированных поверхностях. Каждый тяжёлый повтор — отдельный процесс. Квитанции, снимки зависимостей и изображения сохраняются до удаления окружения. `--runtime` разрешает завершить уже созданную диагностику только в том же прогоне и только при совпадении меток владельца и хеша исходного результата; после проверки том также освобождается.

### SIM-027: моторная rate-модель MANC T1

`simctl.py evaluate --id SIM-027 --no-memory-limit --no-host-reserve` получает два точных Git blob учебного сценария, не расширяя sparse checkout. Уже имеющиеся объекты читаются с отключённой автоматической загрузкой Git; при их отсутствии используется первичный raw URL, максимум две попытки с сохраняемым журналом. Проверяются размер, Git-идентичность и SHA-256. Данные других коннектомов и большие архивы результатов Zenodo не подставляются вместо этих входов.

Временный Linux-том содержит CPU-окружение с JAX 0.6.2 и Diffrax 0.7.0. Зависимости дополнены из авторского `environment.yaml`; фактический lock и `pip check` сохраняются. `test_configs.py` — конфигурационный пример, а не штатная suite. Адаптер отдельно проверяет CLI, уравнение, ориентацию весов и сериализацию малого streaming-checkpoint. Эта проверка не подтверждает восстановление полной HPC-кампании.

Исходное ядро без изменений выполняет восемь двухсекундных сценариев сети из 4604 нейронов: seeds 1/2/3/1, нулевой вход, отключение связей стимулируемого нейрона, изменение временной константы и строгие допуски. Сохраняются NPZ со всеми состояниями, временной осью и bodyId; CSV содержит выбранные моторные трассы. Независимый читатель без импорта модели и JAX проверяет экспорт. Затем строятся графики записанной активности, контрольных условий и штатный график моторных модулей. Артефакты публикуются в [SIM-027](../artifacts/SIM-027/README.md).

Выход — частоты активности, не отдельные спайки. Входная амплитуда не имеет проверенной калибровки в физических единицах. `removeNeurons` отключает связи, сохраняя прямой вход в нейрон; входной шум в rate-уравнении закомментирован. Dopri5 использует адаптивный шаг; 1 мс — сетка сохранения и начальный шаг. Для базового и строгого сценариев отдельно проверяются исходные статусы решателя: штатное ядро заменяет NaN/Inf нулями и ограничивает выход. Отрицательные исходные отсчёты учитываются в квитанциях, а их величина требует дальнейшей оценки. Полный коннектом, тело, биологическая достоверность и электрический оператор этим запуском не подтверждаются.

После публикации результатов окружение удаляется; лишние копии двух входных CSV удаляются только при наличии неизменного оригинала и закреплённого манифеста. README и метаданные заявляют MIT, но отдельного LICENSE/copyright notice и установленной лицензии данных нет; это остаётся ограничением повторного использования.

### SIM-029: авторский browser-worker и интерфейс

```powershell
research/.venv/Scripts/python.exe -B -X utf8 simulations/scripts/simctl.py evaluate --id SIM-029 --no-memory-limit --no-host-reserve
research/.venv/Scripts/python.exe -B -X utf8 simulations/scripts/probes/snedea_reader.py --run research/.work/simulator-evaluation/SIM-029/<run>
research/.venv/Scripts/python.exe -B -X utf8 simulations/scripts/probes/snedea_browser.py --run research/.work/simulator-evaluation/SIM-029/<run>
```

Первый этап использует закреплённый Node-образ, два точных Git blob и семь сценариев по 120 тактов. После 99 штатных программных тестов адаптер добавляет только обнуление `tickCount` в reset рабочей копии; исходный сабмодуль сохраняется. SHA-256 до и после и причина изменения записываются отдельно. Обёртка штатного runner проверяет текстовый итог, поскольку сам runner не гарантирует ненулевой exit при провале теста.

Полные состояния сохраняются как gzip little-endian float32 с размерностью `[tick, worker_index]`, события — как JSON `[tick, worker_index, group_id]`. Сохраняется обратимая перестановка к индексам авторского бинарника. Это не восстановленные FlyWire root_id: их нет в двух runtime-входах. Стандартная библиотека Python независимо проверяет все значения, хеши, размеры, события и перестановку. Такты не объявляются миллисекундами, а состояние — физическим напряжением.

Браузерный контроллер сначала проверяет согласованный сходящийся путь и контроль с нулевыми весами, затем строит график и запускает исходный UI в отдельном профиле установленного Edge. Playwright и lock берутся из `environments/browser-tools/`, а не из временного каталога. Внешние HTTP и все WebSocket блокируются; caretaker/LLM backend не запускается. Поэтому обращения интерфейса к порту 7600 ожидаемо завершаются `ERR_FAILED` и сохраняются в отчёте. Проверяются еда, свет, температура, воздух, касание, очистка еды, пауза/продолжение, масштаб и 3D-схема. Пауза определяется прекращением новых сообщений после завершения уже поставленного такта; сохранённый последний кадр не считается продолжающимся исполнением.

Повторная браузерная проверка создаёт отдельные снимки и квитанции. Она может использовать только прежний диагностический результат с совпадающими SHA-256 сценария и исходного результата. Очищенные входные копии восстанавливаются из проверенного первичного кэша. После проверки сервер и браузер закрываются; профили, npm-кэш и драйвер удаляются общей уборкой. Артефакты публикуются в [SIM-029](../artifacts/SIM-029/README.md). Пустая `NOCI`, виртуальные drives и Canvas-тело исключают вывод о воспроизведённой биологической боли или физическом CAP/ECAP.
