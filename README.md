# Сайдкар `workspace`

Файловая песочница для агента: контейнер на арендатора, в котором можно читать, писать и
выполнять команды, не подпуская их ни к хосту, ни к внутренней сети.

## Зачем отдельный сервис

🔴 **Это единственный сервис, которому отдан `docker.sock`.** Слой `agents` исполняет
управляемый моделью поток для всех арендаторов одним процессом — доступ к демону оттуда
означал бы root на хосте из кода, который пишет модель. Граница проходит здесь и только здесь.

## Три правила, на которых всё держится

1. **Владение — по подписи.** Идентификатор песочницы ездит в теле `/run` и виден в трейсе.
   Без HMAC-токена (`WORKSPACE_OWNER_SECRET`, подписывает backend) угаданный идентификатор был
   бы доступом к чужой файловой системе.
2. **Изоляция подтверждается, а не заявляется.** После создания `docker inspect` обязан
   подтвердить сеть, отсутствие привилегий и добавленных возможностей ядра, режим корня и
   потолки памяти и процессов. Не подтвердил — контейнер уничтожается, песочница не выдаётся.
3. **Статическая половина политики заперта.** Образ, сеть, права на корень, потолки — только
   при создании. Право, доехавшее до работающего контейнера, — повышение привилегий по
   расписанию. Горячими остаются лишь таймаут вызова и потолок вывода.

⚠️ **Убийство хостового `docker exec` не убивает процесс ВНУТРИ контейнера.** Поэтому команда
запускается через `setsid` с записью PGID, а по таймауту группа добивается внутри: иначе
команда модели продолжает жечь процессор арендаторов уже после ответа клиенту.

## Ручки

| метод | путь | что делает |
| --- | --- | --- |
| POST | `/workspaces` | создать песочницу, вернуть токен владения |
| POST | `/workspaces/{id}/exec` | выполнить команду |
| PATCH | `/workspaces/{id}/policy` | горячая правка политики (только незапертые поля) |
| DELETE | `/workspaces/{id}` | удалить |
| GET | `/health` | состояние, драйвер, контракт |

Каждая ручка требует И ключ сервиса (кто зовёт), И токен владения (чья песочница): ключ общий
на весь backend, а песочница принадлежит одному пользователю.

## Драйверы

`WORKSPACE_DRIVER` выбирает рантайм; сегодня известен один — `docker`. Шов заложен сразу:
прод однажды захочет границу прочнее (gVisor, Firecracker, узел Kubernetes), и без шва такая
замена переписывала бы и слой инструментов, и контракт. ⚠️ Неизвестное имя — ошибка, а не
молчаливый откат на docker: опечатка дала бы рантайм слабее заказанного.

`WORKSPACE_DOCKER_SCOPE` задаёт отдельную область инвентаризации Docker
(по умолчанию `1`, прежняя метка `gpthub.workspace=1`). Создание и восстановление
используют одну неизменную метку; другой workspace-процесс не должен обнаруживать
и очищать её контейнеры. Для параллельной dev-приёмки нужен уникальный scope.
Это граница владения инвентарём, а не замена sandbox или отдельные полномочия.
Не менять scope работающего стенда: прежние контейнеры останутся в старой области.

## Разработка

### Шаблоны PDF и перенос на другой сервер

Встроенные форматы находятся в `service/domain/documents/profile_data/`: документ,
статья, отчёт, презентация 16:9, юридический документ, IEEE и AAAI-style.
Эти исходники отслеживаются Git и входят в образ `workspace` через `COPY service`.
Они не зависят от базы данных, Library, MinIO или файлов пользовательской среды.
Проверка `python -m application.documents.bundle_check` при сборке образа требует
весь базовый набор, общие стили и непустые исходники каждого формата. Неполная
поставка останавливает сборку. Тест чистого `git archive` проверяет эти же исходники.

Суперпроект нужно получать вместе с закреплёнными подмодулями:

```sh
git submodule update --init --recursive
make build MODE=prod
make run MODE=prod
```

Перед запуском требуется настроенный `docker/.env.prod` по образцу `.env.example`.
`make build` собирает как сервисы, так и отдельные runtime-образы workspace/LaTeX;
одного `docker compose up --build` для runtime-образов недостаточно.
Production-данные и секреты из dev переносить для базовых шаблонов не нужно.
Сторонние издательские пакеты остаются отдельными проверяемыми project-local
загрузками: встроенный AAAI-style не обещает официальный издательский комплект.

`AGENTS__WORKSPACE_AUTOCREATE=false` — безопасный штатный режим. Он запрещает
неявное выделение контейнера обычным чатом, но не чтение каталога и не действия
пользователя с выбранным проектом. Если API `document-profiles` отвечает ошибкой,
проверяют обновление backend, доступность workspace, адрес и совпадение сервисного
ключа, а не включают автосоздание или копируют пользовательские шаблоны вслепую.

```sh
uv sync --extra dev
uv run --extra dev pytest -q      # docker не нужен: драйвер подменяется
uv run --extra dev ruff check .
```

### Приёмка заранее установленного pytest

`docker/harness-pytest.Dockerfile` — отдельный тестовый образ поверх
`gpthub-workspace-runtime:harness-dev`. Он устанавливает pytest и его зависимости
из `docker/acceptance/pytest-requirements.txt` с проверкой версий и хешей колёс.
Обычный runtime не меняется. Это не автоматическая установка зависимостей проекта:
код пользователя по-прежнему работает без сети, с корнем только для чтения
и под непривилегированным пользователем.

При уже собранном базовом образе из каталога `workspace`:

```sh
docker build -f docker/harness-pytest.Dockerfile -t gpthub-workspace-runtime:harness-pytest .
```

Реальная проверка через backend, снимки, журнал и supervisor находится в
`backend/tests/test_harness_verification_services_live.py` суперпроекта и включается
явно через `HARNESS_VERIFICATION_SERVICES_LIVE=1`. Тестовый образ выбирается только
для сценариев установленного pytest в отдельном workspace-процессе. Постоянный
стенд, пользовательские проекты и harness-флаги эта проверка не переключает.
