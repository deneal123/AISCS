# backend — ядро платформы GPTHub

FastAPI + celery. Владеет всем, что относится к платформе как к продукту: пользователи и
доступ, чаты и их история, файлы, биллинг и платежи, админ-панель, уведомления, аналитика.

Чего здесь **нет** и не должно быть: агентного движка. Он вынесен в сайдкар `agents` —
там мультипровайдерный LLM-слой, роутинг, инструменты и стриминг. Backend разговаривает
с ним по HTTP (`service/infrastructure/agents_client/`), а деньги списывает сам, из
результата прогона.

## Структура

```text
service/
  main.py            сборка ASGI-приложения
  settings.py        конфигурация (pydantic-settings, синглтон на импорте)
  composition/       DI-контейнер: что из чего собирается
  services/<домен>/  вертикальные срезы, у каждого свои слои:
      domain/          бизнес-правила
      application/     сценарии, порты
      infrastructure/  адаптеры к внешнему миру
      persistence/     репозитории
      presentation/    HTTP/WS-роутеры
  infrastructure/    общие адаптеры (БД, кэш, хранилище, очередь, почта, agents_client)
  models/            ORM-модели и перечисления
  shared/            то, чем пользуются несколько срезов
alembic/             миграции схемы
tests/               см. ниже
```

Срезы: `admin`, `analytics`, `billing`, `chat`, `files`, `jobs`, `notifications`,
`profile`. Слои внутри среза обязательны не все — они появляются по мере надобности.

## Запуск

Через compose суперпроекта, а не отдельно: сервису нужны Postgres, Redis, MinIO и
сайдкары. Из корня монорепо:

```sh
make run                 # dev-стек
make run MODE=prod
make create-user EMAIL=you@example.com PASSWORD=secret123
```

⚠️ Контекст сборки образа — **корень суперпроекта**, а не этот каталог: Dockerfile
копирует по путям вида `./backend/…`. Сборка с контекстом `../backend` не соберётся.

## Тесты

```sh
cd backend && python -m pytest            # с гейтом покрытия из pytest.ini
python -m pytest tests --no-cov           # быстро, без покрытия
make test-cross-service                   # из корня: требует ОБЕ половины
```

`tests/cross_service/` — тесты, написанные во времена монолита: им нужен и backend, и
движок из сайдкара. В обычном прогоне они пропускаются, и это осознанно — молчаливый
«зелёный» хуже отсутствующего теста, поэтому запускаются они отдельной целью.

Стражи, на которые опирается разделение сервисов:

| Тест | Что держит |
|---|---|
| `test_service_boundary.py` | backend не импортирует код сайдкара (в т.ч. лениво) |
| `test_contract_parity_with_sidecar.py` | контракт совпадает с ЖИВЫМ сайдкаром |
| `test_shared_vectors.py` | раздвоенные `net_guard`/`token_estimate`/`model_class` не разошлись |
| `test_ports_contracts.py` | порты движка не изменились молча |

## Границы

* **Провод с сайдкаром** описан своей копией в `infrastructure/agents_client/contracts/`.
  Общего пакета намеренно нет: он означал бы согласованный релиз двух сервисов при
  каждой правке контракта. Расхождение ловят стражи выше и офлайн-сверка в CI.
* **Деньги** считаются здесь. Воркер списывает из result-dict `/run` и отдельно из
  `routing_usage` — оба поля покрыты контрактом, потому что читаются как
  `.get(...) or 0` и молча дают ноль при переименовании.
* **Секреты** в реестр настроек админки не вносятся; провайдерские ключи из БД
  пушатся в сайдкар снимком (`POST /providers/keys`).
